An assistant for cancho that proves its work

Every task ends in a machine-readable verdict produced by the type checker and by examples written before the code — not by what the model says about itself. The agent is any model: a local one over Ollama, or a cloud one over native HTTPS. The loop is bounded by contracts, so a run that stops names its stop.

Why

Most coding assistants hand you a transcript and ask you to read the diff. cancho-code hands you a verdict:

[ISSUE_VERDICT]	verified	attempts 1

The model does not decide when it is done. The compiler does. A run of the loop is: the agent edits the file, cancho check --output json answers, the loop decides — retry, stop the issue, stop the run — and after a verified answer it checks again before believing it, then snapshots it. Every way the run can end prints one named verdict line; there is no state in which it runs silently.

The failure it is built not to repeat is lex-code's own, measured and documented there: runs that continue for a long time without solving anything. Loop-safety here is contracts with defaults, not tuning flags — and each one has a gate where a stand-in loops forever and the assertion is that the loop stops, in seconds rather than hours.

Run it

Build the fix tool from a checkout of this repository, with the compiler's packages beside it:

git clone https://github.com/alpibrusl/cancho-code.git
cd cancho-code
export CANCHO=<path-to-the-cancho-binary>
export CANCHO_PACKAGES=<compiler-checkout>/packages

"$CANCHO" build tests/programs/fix.cho \
    src/driver.cho src/checker.cho src/signature.cho \
    src/loop_check.cho src/snapshot.cho \
    --std --backend cranelift -o ./fix

Then point it at a broken program and an agent:

./fix "$CANCHO" project.cho "scripts/agent-ollama.sh" 4

The three arguments are the compiler (by its absolute path — the child of exec_spawn gets no PATH of its own), the file to fix, and the agent: any shell command that edits the file. The fourth is the attempt ceiling. Exit codes: 0 verified, 1 the budgets named a stop, 2 usage, 3 the checker or the agent is away — a wait, rerun.

A realistic walkthrough: Ollama, qwen3.8:27b, a broken program

This is the whole point of the tool, end to end, on one machine: a local model with no key and no egress, a real program with a real error, and a compiler that decides when the model is done.

1. Install Ollama and pull the model

curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen3.8:27b

27B wants a machine with roughly 20 GB of memory to spare; on a laptop-class machine a whole run takes minutes, not seconds. That is fine — the budgets are in attempts and turns, not milliseconds.

2. Make a program with a real error

mkdir demo && cat > demo/wordcount.cho <<'EOF'
edition 7;

// A broken word counter. Two errors, deliberately the same rule with
// different messages, so a model that fixes one and not the other
// changes the failure signature and gets its full budget back.
fn counts[&i](io: &!i Io) -> [io_read] int {
    var words = 0;
    var inside = false;
    var c = getchar(io);
    while c >= 0 {
        if c == 32 || c == 10 {
            inside = false;
        } else {
            if inside == false {
                words = words + 1;
            }
            inside = true;
        }
        c = getchar(io);
    }
    return inside;
}

fn label(total: int) -> [] int {
    if total > 0 {
        return "many";
    }
    return 0;
}

fn main(world: World) -> [] int {
    let Split { io, ffi, fs, heap, args, net, clock, signals, exec } = split(world);
    release(ffi); release(fs); release(net); release(clock);
    release(signals); release(exec); release(args);
    release(io);
    release(heap);
    return 0;
}
EOF

Two errors, both type-mismatch with different messages: counts returns a bool where its signature says int, and label returns a string where it says int. The checker answers both in one pass:

"$CANCHO" check demo/wordcount.cho --output json --backend cranelift

3. Run the loop with the local model as the agent

export OLLAMA_MODEL=qwen3.8:27b
./fix "$CANCHO" demo/wordcount.cho "$(pwd)/scripts/agent-ollama.sh" 4

What happens, turn by turn:

  • The driver runs scripts/agent-ollama.sh demo/wordcount.cho: the script pipes the file and the instruction ("reply with the complete corrected file") into ollama run qwen3.8:27b, strips any markdown fence, and overwrites the file with the answer.
  • The driver runs the real cancho check --output json on the result. The model's word is worth nothing here; the checker's JSON is the only oracle.
  • signature.of turns the refusal into a failure signature — the rule verbatim, the message with its backticked spans kept and numbers normalised — and loop_check.decide decides with the §4 budgets: attempt ceiling 4, same-signature stop at K=2.
  • If the model fixes counts and not label: the signature changes ("expected int, found bool" becomes "expected int, found a string"), the counter resets, the loop tries again — a struggling model gets its full budget.
  • If the model returns the same wrong answer twice: the same-signature stop fires — [ISSUE_VERDICT] failed signature — and the run ends, named, instead of burning the night.
  • When the check says clean: the driver checks again (the re-verify pass) and only then snapshots the file and prints [ISSUE_VERDICT] verified attempts N.

4. What a good run looks like

$ ./fix "$CANCHO" demo/wordcount.cho "$(pwd)/scripts/agent-ollama.sh" 4
[ISSUE_VERDICT]	verified	attempts 2
$ echo $?
0
$ "$CANCHO" check demo/wordcount.cho --output json --backend cranelift
{
  "refused": []
}

Done is a proof, not a status.

5. What a bad run looks like (and why it is cheap)

A model that keeps answering with the same broken shape stops on the second identical refusal:

[ISSUE_VERDICT]	failed	signature
$ echo $?
1

The snapshot ring beside the file (demo/wordcount.cho.snapshots/) holds the newest state that checked clean, so a stopped run loses nothing: fix the prompt, rerun, the loop resumes from what the checker last believed.

Cloud models

The same loop drives a cloud provider over native HTTPS — scripts/test-provider.sh mistral with MISTRAL_API_KEY in the environment runs the end-to-end gate against the real API, the checker still the oracle. The provider is written in cancho on packages/http-client and packages/tls; the key rides the Authorization header and exists nowhere else.

The loop-safety contracts

ContractRuleDefault
Attempt ceilingattempts per issue before it is given up on, named4
Same-signature stopK consecutive identical failure signatures end the issue — the rule lex-code left open: it grouped failures to report, never to stopK = 2
Plan defects never retriedthe store's word, not how the failure looksalways on
Re-verify passcheck again before believing a verified; a regressed file goes back on the boardalways on
Snapshot and restorethe newest state that checked clean is one restore awayring of 8
Outages are waitsa checker or agent that never answers is a named stop, attempts preservedalways on

Each one has a gate: scripts/test-checker.sh, test-snapshot.sh, test-driver.sh (three cases: a fix verifies in one attempt; a looping agent stops at the signature rule; a cycling agent gets its full ceiling). Thirteen unit tests cover the decision functions and the signature normalisation.

Status and limits, stated plainly

  • Built: the decision module, the failure signature, the subprocess checker driver, the snapshot ring, the composed loop with its verdict lines, the Mistral provider over native HTTPS, the Ollama agent script, the fix front door. All gates green in CI without a network or a key.
  • Not built: the typed-issue board (issue #2 — which issue is next, what regressed), the report (issue #5), the authority pin in CI (issue #6).
  • The local-model path shells out to ollama through the Exec capability: the tool's authority report names the one directory its agents may live in.
  • Measured on this repo's own gates, four silent false-passes were found and fixed by the gates themselves, not by review: a reversed-signature normalisation, a shell $0 argv bug, an edition-less fixture, a negative ring position.
