Build a cancho service, the application half of an HTTP program, named "users": a small JSON API for user records, with a validated request body, errors reported as problem documents and an OpenAPI document served by the program itself. The server loop (accepting connections, parsing requests with std.http, sending answers) is a fixed file you do not write; you write project.cho, which defines the application.

THE LIBRARIES. Two existing cancho libraries are compiled into the program, and project.cho already imports them (`import schema;` and `import web;`): you are expected to use them, not to write routing, body validation or the API document by hand.
  cancho-web, module `web`: declare an API once and get from the declaration the router, the checking of path and query parameters, and the OpenAPI 3.1 document. Entry points: web.empty, web.operation, web.internal, web.query_param, web.path_param, web.default_int, web.body, web.respond, web.respond_empty, web.respond_problem, web.response_header, web.component, web.most_params, web.most_args, web.slot, web.dispatch, web.answered, web.int_arg, web.openapi, web.drop.
  cancho-schema, module `schema`: describe the shape of a JSON value as data and check a body against it, reporting every fault. Entry points: schema.empty, schema.new_string, schema.new_int, schema.new_array, schema.new_object, schema.add_field, schema.slot_count, schema.errors_len, schema.validate, schema.problem, schema.to_int, schema.int_max, schema.drop.
Both libraries are in the same style as the rest of cancho (values passed by value come back by value, `heap` is passed to whatever allocates).

THE INTERFACE. project.cho starts with "edition 7;" and defines exactly (these signatures are fixed):

    struct App { ... }                      the service state, any fields
    fn app_new[&h, &c](heap: &!h Heap, config: &c [byte]) -> [heap] App
    fn app_handle[&h, &a, &q, &t, &b](heap: &!h Heap, app: &!a App, request: &q [byte], table: &t [int], body: &b [byte], now_ms: int, out: buffer.Buffer) -> [heap] buffer.Buffer
    fn app_drop[&h](heap: &!h Heap, app: App) -> [heap] int

`config` is the command-line flags after the program name (this service takes none, ignore it). `request` and `table` are one parsed request (std.http: http.method, http.path, http.query, http.header(request, table, "content-type") ...), `body` its body, `now_ms` the clock in milliseconds (unused here), and `out` an empty buffer to append the answer to with server.reply(heap, out, status, body, keep), server.reply_as(heap, out, status, content_type, body, keep, extra_header_lines) or server.reply_empty(heap, out, status, keep, extra_header_lines), where keep = http.keeps_alive(table). app_handle must answer every request and never trap. Do NOT import std.buffer, std.bytes, std.http, std.io, std.json, std.map, std.option, std.result, std.route, std.vec or http.server: the fixed file imports them for the whole program, and you use them qualified (buffer., bytes., http., json., server. ...).

Users live in memory for the life of the process; nothing is persisted. The store is fixed in size (a borrowed App cannot grow a collection): at most 200 users are ever created (a deleted user still counts), the 201st POST is 503. The server binds its port on all interfaces.

ENDPOINTS. A user is {"id": integer, "name": text, "age": integer}. Ids are 1, 2, 3 ... in order of creation and are never reused, not even after a delete.

POST /users -- create a user. The body is a JSON object with exactly the fields "name" (text of 1 to 40 characters, counted in Unicode code points) and "age" (a whole number from 0 to 150), both required, no other field allowed. The Content-Type must be application/json (any letter case, parameters such as "; charset=utf-8" allowed). The checks run in this order and the first failure answers:
    1. Content-Type is not application/json     -> 415 problem document
    2. the body is not valid JSON               -> 400 problem document
    3. the body breaks the rules above          -> 422, EVERY fault at once (see below)
    4. 200 users have already been created      -> 503 problem document
  On success: 201 with the user as JSON, Content-Type application/json, and the header "Location: /users/<id>". The answer is the user exactly as it is stored: "name" with the text decoded and encoded again, and no other field.

GET /users?limit=N -- 200 {"total": <number of users that exist now>, "items": [<the first N users, ordered by id ascending>]}. N is a whole number from 1 to 100 and defaults to 20. "total" counts every existing user, not only those on the page; a deleted user is in neither. A limit outside 1..100 or not a number, or a repeated limit, or any other query parameter, is 422 (see below) with the fault at "/query/limit" (or "/query/<name>" for an unknown parameter).

GET /users/{id} -- 200 with the user, or 404 problem document if no such user exists (never created, or deleted). An id that is not a whole number from 1 up (0, -1, abc, 1.5) is 422 with the fault at "/path/id".

DELETE /users/{id} -- 204 with no body, and the user no longer exists (a second DELETE and a GET are 404 problem documents). An invalid id is 422 as above.

GET /openapi.json -- 200, the OpenAPI 3.1 document of this API as JSON (the "openapi" field is "3.1.0"), generated from the same declarations that route and validate, not written by hand: its "paths" are "/users" (get and post) and "/users/{id}" (get and delete), with these operationIds listUsers, createUser, getUser, deleteUser; the limit parameter of listUsers is an integer with minimum 1, maximum 100 and default 20; the request body of createUser has "name" (string, minLength 1, maxLength 40) and "age" (integer, minimum 0, maximum 150) both required, no additional properties; the responses of each operation list exactly the statuses the endpoints above can answer (listUsers 200 and 422; createUser 201, 400, 415, 422 and 503; getUser 200, 404 and 422; deleteUser 204, 404 and 422), and each response says what its body is: a user for the 201 of createUser (which also documents its Location header) and for the 200 of getUser, a page (total and items) for the 200 of listUsers, no body for the 204, and for every error status the problem document with Content-Type application/problem+json, one shared description that the error responses refer to (a complete document: every reference in it resolves). The document is a part of the program that is served, so what it says and what the service does must agree.

Any other path is 404 and a known path with another method is 405 with an "Allow" header listing the methods that path has (the `web` library answers both when it is asked to dispatch a request).

PROBLEM DOCUMENTS. Every error answer of 400, 404, 415, 422 and 503 has Content-Type application/problem+json and a JSON object with "type" (the text "about:blank"), "title" (the standard phrase of the status), "status" (the status as an integer) and "detail" (text). The 422 for a body (and the 422 of `web` for a path or query parameter) lists EVERY fault in one answer instead of "detail": {"type": "about:blank", "title": "Unprocessable Content", "status": 422, "count": <number of faults>, "errors": [{"pointer": "/age", "code": "maximum", "detail": "..."}, ...]}. "pointer" is the JSON Pointer of the faulty value in the body ("" for the whole body, "/name" for a field), or "/query/limit", "/path/id" for a parameter; for a missing required field it names the missing field. "code" is one of required, type, minimum, maximum, min_length, max_length, unknown (a field the schema does not have), duplicate and range, as the `schema` and `web` libraries report them; the order of the errors does not matter and the texts of "detail" are not checked. This is exactly the document `schema.problem` writes for a body.

AUTHORITY. The program may declare only these effects: args, heap, clock, net_in, conn_accept, conn_read, conn_write, poll, io_write, err_write (the fixed server file declares them; your project.cho needs only heap). It must never need a process, a file or foreign code.

PURE FUNCTIONS. The following decisions must be written as pure functions (empty effect row `[]`, no heap), with exactly these names and signatures, each with examples in your plan or tests; app_handle only calls them:
    fn json_type_ok[&c](value: &c [byte]) -> [] bool       a Content-Type value is application/json: "application/json" yes, "Application/JSON" yes, "application/json; charset=utf-8" yes, "application/json ;x" yes, "application/jsonx" no, "text/json" no, "" no, "application/jso" no
    fn has_room(count: int, used: int, add: int) -> [] bool    may one more user be stored: `count` users were stored so far, `used` bytes of the row arena are taken, the new row is `add` bytes. True only when count < 200 and used + add <= 65536: (0, 0, 100) yes, (199, 0, 10) yes, (200, 0, 10) no, (5, 65526, 10) yes, (5, 65527, 10) no
