Build a cancho service, the application half of an HTTP program, named "webhooks": a signed-webhook inbox REST API that is safe to put on the internet. The server loop (accepting connections, parsing requests with std.http, sending answers) is a fixed file you do not write; you write project.cho, which defines the application. Use std.hmac (HMAC-SHA256) for the signature and std.json / std.http for the rest; you write no cryptography of your own.

THE INTERFACE. project.cho starts with "edition 7;" and defines exactly (these signatures are fixed):

    struct App { ... }                      the service state, any fields
    fn app_new[&h, &c](heap: &!h Heap, config: &c [byte]) -> [heap] App
    fn app_handle[&h, &a, &q, &t, &b](heap: &!h Heap, app: &!a App, request: &q [byte], table: &t [int], body: &b [byte], now_ms: int, out: buffer.Buffer) -> [heap] buffer.Buffer
    fn app_drop[&h](heap: &!h Heap, app: App) -> [heap] int

`config` is the command-line flags after the program name, each flag and each value followed by a newline ("--secrets\nalpha:k1\n--admin-token\nT\n"; "--port N" is consumed by the server). `request` and `table` are one parsed request (std.http: http.method, http.path, http.query, http.header(request, table, "x-signature") ...), `body` its body, `now_ms` the clock in MILLISECONDS SINCE 1970-01-01 UTC, and `out` an empty buffer to append the answer to with server.reply(heap, out, status, body, keep) or server.failure(heap, out, status, message, keep), where keep = http.keeps_alive(table); failure writes {"error": message}. app_handle must answer every request and never trap. Do NOT import std.buffer, std.bytes, std.http, std.io, std.json, std.map, std.option, std.result, std.route, std.vec or http.server: the fixed file imports them for the whole program, and you use them qualified (buffer., bytes., http., json., server. ...). Other std modules (std.hmac, std.crypto, std.utf8 ...) you import yourself.

CONFIGURATION (flags, because a cancho program has no environment variables):
  --secrets "source1:secret1,source2:secret2"   a source name is 1 to 32 characters of lowercase letters, digits, "_" or "-"; a secret is one or more characters, none of them "," or ":" (it may contain spaces and any other character). If the flag is missing or its text is not of this form, the service has NO sources (every delivery is then 401).
  --admin-token TOKEN                           the bearer token for reading events: one or more printable ASCII characters other than space. If the flag is missing or invalid, no token is accepted (GET /events is always 401).
Events live in memory for the life of the process; nothing is persisted and nothing needs to survive a restart (cancho has no SQL and no database; this replaces the SQLite store of the Lex original). The server binds its port on all interfaces (a cancho listener takes a port, not an address, so the loopback-only requirement of the original does not exist here).

ENDPOINTS, all answering JSON. Any other path is 404 {"error":...}; a known path with another method is 405 {"error":...} (GET on /hooks/{source}, anything but GET on /events).

POST /hooks/{source} -- a sender delivers one event. {source} is the rest of the path after "/hooks/" (a single segment; an empty segment or one containing "/" is 404). Headers: "X-Timestamp" (integer Unix seconds), "X-Event-Id" (1 to 64 characters of letters, digits, "_" or "-") and "X-Signature" of the form "sha256=" followed by exactly 64 lowercase hex characters. The signature is HMAC-SHA256, keyed with the source's secret, of the text <X-Timestamp header text> + "." + <raw request body bytes>. The body must be a JSON object. On success: 202 with {"id": <integer>, "duplicate": false}, and the event (source, event id, receive time, body) is stored. If the same source has already stored the same X-Event-Id, nothing is stored again and the answer is 200 with {"id": <the id of the first one>, "duplicate": true}. The same event id from different sources is independent. Event ids are positive integers that increase with arrival.
  The checks run in this order and the first failure answers:
    1. body longer than 256 bytes                       -> 413 (for any source, signed or not)
    2. unknown source, or X-Signature missing/malformed/wrong -> 401 {"error":"unauthorized"}
    3. X-Timestamp missing, not 1 to 12 ASCII digits, or outside the window -> 400
    4. X-Event-Id missing or invalid                     -> 400
    5. body not a JSON object (array, string, number, invalid JSON, empty) -> 400
    6. the event store already holds 1000 events and this one would be new -> 503 {"error":...} (a duplicate is still answered 200)
  The signature is computed over the X-Timestamp header text exactly as received (the empty text if the header is absent) and over the body bytes exactly as received, BEFORE the body is parsed; that is why a request with a missing or non-integer X-Timestamp is 401 unless its signature happens to be valid for that text, in which case it is 400.
  A body larger than the server's 16 KiB input buffer never reaches the application: the server answers 413 itself. (The Lex original allowed 65536 bytes; a cancho answer must fit the server's 64 KiB output buffer, and a page of 100 events must fit it, so bodies are limited to 256 bytes here.)

GET /events?source=NAME&limit=N -- requires "Authorization: Bearer <admin token>" (exactly "Bearer", one space, the token; anything else is malformed). Returns 200 {"events": [...]} ordered by id ascending, the first N matching events, each {"id": int, "source": "...", "event_id": "...", "received_at": <integer Unix seconds when it was received>, "body": <the JSON object that was sent>}. "source" is optional and, if present, must be exactly the name of a configured source (no percent-decoding: anything else, an empty value included, is 400). "limit" is optional, 1 to 100 written as plain digits without sign or leading zero, default 50 (anything else, an empty value included, is 400). Authentication is checked first: without the token, with a wrong token or with a malformed Authorization header the answer is 401 whatever the query says.

SECURITY REQUIREMENTS. Each is something an attacker will try, and each must hold:
 1. A missing, malformed or wrong X-Signature is 401 and nothing is stored. The signature covers the raw body bytes as received. A valid signature for one source is not accepted for another (different secrets). Uppercase hex is malformed.
 2. An unknown source and a bad signature give the IDENTICAL 401 response (same status, same body), so an attacker cannot learn which sources exist.
 3. Signatures and the admin token are compared in constant time (no early exit on the first differing byte), and secrets and the admin token are never echoed in any response.
 4. Replay protection: X-Timestamp must be within 300 seconds of the server's clock (now_ms / 1000), past or future, 300 itself included; otherwise 400 and nothing is stored.
 5. A body of more than 256 bytes is 413 before the signature is looked at. A body that is not a JSON object is 400, after the signature has been verified (an unsigned request is always 401, never 400).
 6. GET /events without the token, with a wrong token or a malformed Authorization header is 401 and nothing is read; the token is compared in constant time. A "source" value such as a' OR '1'='1 is simply not a configured source (400).
 7. The store holds at most 1000 events (fixed capacity: a borrowed App cannot grow a collection); see check 6 above.

PURE FUNCTIONS. The logic below must be written as pure functions (empty effect row `[]`, no heap), with exactly these names and signatures, each with examples in your plan or tests; app_handle only calls them:
    fn name_ok[&s](name: &s [byte]) -> [] bool                  "alpha" yes, "A" no, "" no, 33 characters no
    fn event_id_ok[&s](id: &s [byte]) -> [] bool                "Evt_1-a" yes, "a b" no, 64 characters yes, 65 no
    fn secrets_ok[&s](text: &s [byte]) -> [] bool               "a:x,b-2:y z" yes; "a" no, "a:" no, "A:x" no, "a:x:y" no, "" no
    fn secret_span[&s, &n](text: &s [byte], name: &n [byte]) -> [] (int, int)   "a:xy,b:z" with "b" -> (7, 8); absent -> (-1, -1)
    fn timestamp_value[&s](text: &s [byte]) -> [] int           "1700000000" -> 1700000000; "" , "-5", "12a", 13 digits -> -1
    fn timestamp_in_window(ts: int, now_s: int) -> [] bool      (1000, 1300) yes, (1000, 1301) no, (1300, 1000) yes, (1301, 1000) no
    fn signed_text[&t, &b, &o](ts: &t [byte], body: &b [byte], out: &!o [byte]) -> [] int   writes ts "." body into out, answers its length, or -1 if out is too small
    fn signature_decode[&s, &o](header: &s [byte], out: &!o [byte]) -> [] bool   "sha256=" + 64 lowercase hex -> true and the 32 bytes in out[0..32]; anything else false
    fn same_bytes[&a, &b](x: &a [byte], y: &b [byte]) -> [] bool   equal length and contents, with no early exit on the first difference
    fn token_ok[&s](text: &s [byte]) -> [] bool                 one or more printable ASCII characters other than space
    fn bearer_span[&s](header: &s [byte]) -> [] (int, int)      "Bearer abc" -> (7, 10); "bearer abc", "Bearer", "Bearer ", "Bearer a b", "Basic x" -> (-1, -1)
    fn limit_value[&s](text: &s [byte]) -> [] int               "7" -> 7, "100" -> 100; "", "0", "101", "05", "+5", "x" -> -1
    fn flag_span[&c, &f](config: &c [byte], flag: &f [byte]) -> [] (int, int)   in "--a\n1\n--b\n2\n", flag "--b" -> (10, 11); absent -> (-1, -1)

AUTHORITY. The program may declare only these effects: args, heap, clock, net_in, conn_accept, conn_read, conn_write, poll, io_write, err_write (the fixed server file declares them; your project.cho needs only heap). It must never need a process, a file or foreign code. HMAC-SHA256 and the constant-time compare are ordinary pure code in cancho and need no capability.
